## 아키텍처·인프라

어디서 무엇을 돌리고, 큐·틱을 어떻게 두는지.

<a id="d-09"></a>

### D-09 중앙은 Vercel+Supabase, 나머지는 AWS

- **결정**
  - 중앙 핵심(콘솔, Postgres, 에스컬레이션)은 Vercel + Supabase(서울).
  - AWS에서만 가능한 것(고객 이벤트 수집, 알람 엔진, IAM 연동)은 AWS.
  - 모든 알림은 AWS 수집 + SQS 경유
- **이유**
  - PoC 속도, 관계형 데이터 적합.
  - 나중에 전부 AWS로 옮길 때 고객 쪽 변경 없음
- **확정일**: 11/9

<a id="d-10"></a>

### D-10 운영 조건(Pro·PITR·heartbeat)

- **결정**: 운영 조건: Vercel Pro, Supabase Pro + PITR, 1분 에스컬레이션 + heartbeat, SQS DLQ 알림, prisma migrate
- **이유**: 기존 alert-hub의 하루 1회 cron, db push 결함 재발 방지
- **확정일**: 11/9

<a id="d-22"></a>

### D-22 SQS 큐 2개 + 각 DLQ

- **결정**
  - SQS 큐는 2개: 들어온 알림(alert-events), 알람 작업(alarm-commands).
  - 각각 DLQ
- **이유**: "SQS만 쓴다"는 기술 한정이지 개수 제한이 아님
- **확정일**: Q-API-01

<a id="d-23"></a>

### D-23 1분 틱은 pg_cron

- **결정**
  - 1분 틱은 PoC에서 Supabase pg_cron(+pg_net)으로 엔드포인트 호출.
  - AWS 이전 때 EventBridge Scheduler로 교체
- **이유**: PoC 속도 우선, 교체 범위는 호출 1곳
- **확정일**: Q-API-02

<a id="d-48"></a>

### D-48 alarm-commands는 표준 SQS

- **결정**
  - **확정(사용자 결정, 11/13, Q-API-15 닫힘).**
  - `alarm-commands`는 **표준 SQS 큐**.
  - 중복 전달은 엔진이 `commandId`로 한 번만 처리한다.
  - SSE, DLQ(maxReceiveCount 5), DLQ 비어 있지 않음 알람.
  - 발행기는 FIFO URL도 지원하지만 쓰지 않는다
- **이유**
  - 해지 명령은 순서보다 한 번 처리가 중요하고 멱등이 이미 있다.
  - FIFO는 한 고객이 막히면 그 고객 줄 전체가 멈춘다
- **확정일**: 11/13 (사용자 결정)

<a id="d-49"></a>

### D-49 Vercel OIDC로 AWS 호출

- **결정**
  - **확정(사용자 결정, 11/13, Q-API-03 닫힘).**
  - Vercel 콘솔은 **Vercel OIDC로 IAM 역할을 맡아** AWS를 부른다.
  - 장기 접근 키를 두지 않는다.
  - 역할 신뢰는 OIDC `sub`/`aud`로 이 Vercel 프로젝트·production 환경에 고정하고, 권한은 `alarm-commands` 큐 ARN의 `sqs:SendMessage` 하나
- **이유**: 유출될 장기 비밀이 없고 회전 부담이 없다(security 검토 sqs-command-publisher 권고)
- **확정일**: 11/13 (사용자 결정)

## AWS 연동·고객 권한

고객 AWS 계정에 두는 역할과 자동 조치.

<a id="d-07"></a>

### D-07 고객 IAM 역할 목적별 분리

- **결정**
  - 고객 IAM 역할 목적별 분리, 스택 하나: Reader·EventForwarder(필수), AlarmWriter·TagWriter·Remediator(선택).

  - ExternalId 필수, 특정 중앙 역할만 신뢰
- **이유**: 고객 보안 심사, RCA 에이전트는 읽기 전용이어야 함, 선택 기능은 고객이 고름
- **확정일**: 11/9 (11/9 Q-02로 TagWriter 추가)

<a id="d-15"></a>

### D-15 자동 조치(고객사별 선택)

- **결정**
  - 자동 조치(무단 변경 시 EC2·RDS 중지, ELB 삭제) 포함.
  - 고객사별 선택(기본 꺼짐), 처음엔 알림만 모드, 실제 실행은 Slack에서 사람 승인.
  - 권한은 Remediator 역할에만
- **이유**: 기존 기능 유지, 과격한 동작이라 안전장치 필수
- **확정일**: 11/9 (Q-01)

<a id="d-47"></a>

### D-47 EventForwarder ExternalId 예외

- **결정**
  - **확정(사용자 결정, 11/13). D-07 예외.**
  - 고객 스택의 **EventForwarder** 역할은 `events.amazonaws.com`(고객 계정 안의 EventBridge)이 맡으므로 `sts:ExternalId`를 쓸 수 없다.
  - 대신 신뢰 조건을 `aws:SourceAccount`=그 계정, `aws:SourceArn`=`rule/AlarmOps-*`로 고정하고, 권한은 중앙 버스 ARN 하나에 `events:PutEvents`만 준다.
  - 중앙 버스는 `events:source aws.*`와 정해진 detail-type만 받고, 수집기는 이벤트 최상위 `account`만 믿는다.
  - 나머지 4개 역할(Reader·AlarmWriter·TagWriter·Remediator)은 D-07대로 ExternalId 필수
- **이유**
  - AWS 서비스 주체는 ExternalId를 보내지 않는다.
  - SourceAccount/SourceArn이 AWS 표준의 confused-deputy 방어다.
  - 중앙 계정은 이 역할을 맡지 않는다(security 검토 infra-d43: 수용 가능)
- **확정일**: 11/13 (사용자 결정)

## 알람·임계치

<a id="d-08"></a>

### D-08 임계치 저장 위치·알람 이름

- **결정**
  - 임계치: 리소스 태그(Threshold_*)는 읽기만(최우선).
  - 콘솔 변경은 우리가 만든 알람에 저장.
  - 중앙 DB는 변경 기록.
  - 알람 이름에는 임계치를 넣지 않음(리소스 + 지표로 고정, 변경은 제자리 수정)
- **이유**: 고객 IaC(Terraform) 관리 주체와 무관하게 영향 최소화, 값이 고객 계정에 남아 유실 대비
- **확정일**: 11/9

<a id="d-16"></a>

### D-16 Monitoring 태그와 "확인 필요"

- **결정**
  - `Monitoring=on` 태그는 고객이 붙이거나 TagWriter로 콘솔이 붙임.
  - 태그가 밖에서 사라져도 알람을 지우지 않고 "확인 필요"로 표시
- **이유**: Terraform 등이 태그를 지워 알람이 삭제되는 사고 방지

### D-37 SMS·음성은 확인된 번호로만

- **결정**
  - **확정(사용자 승인).**
  - **SMS·음성은 확인된 번호로만 보낸다**(기본 켜짐. **코드에 넘기는 값**은 불리언 `false`일 때만 끈다 — 문자열 `'false'`·`0` 등은 켜진 채다. **환경 변수 `SMS_VOICE_REQUIRE_VERIFIED`**는 로더(`loadPolicyFlags`)가 읽으며 `false`·`0`·`no`·`off`(대소문자 무시)만 끈다. 빈 값·오타·모르는 값은 켜진 채로 두고 시작할 때 경고를 남긴다).

  - 대신 "보냈다고 생각했는데 안 갔다"가 숨지 않게 기록·표시한다

## 고객 상태·데이터 보관

정지·해지 고객과 데이터 보관 기간.

<a id="d-42"></a>

### D-42 Customer.status와 포털 차단

- **결정**
  - **확정(사용자 결정).**
  - **`Customer.status`**(`ACTIVE`·`SUSPENDED`·`TERMINATED`, 기본 `ACTIVE`, 마이그레이션 `0003_customer_status`).
  - `ACTIVE`가 아닌 고객의 **포털 사용자는 세션이 없다**: `sessionPrincipal`이 null → 401(요청마다 확인).
  - **MSP 직원은 영향 없음**(그 고객 데이터도 계속 본다).
  - 데이터는 지우지 않는다.
  - 메모리·SQL 저장소 같은 동작, 공용 계약 테스트로 고정.
  - **남은 것:** 상태를 바꾸는 API·콘솔 화면 없음(DB에서만 바꾼다).
  - **수집·틱은 바꾸지 않았다** — `ACTIVE`가 아닌 고객의 이벤트 수집·호출을 어떻게 할지는 열린 질문(DATA-MODEL Q-DM-20)
- **이유**
  - 계약이 끝나거나 멈춘 고객의 담당자가 포털에 계속 들어오는 것을 막는다.
  - 사용자를 하나씩 끄지 않아도 고객 하나로 끊긴다.
  - 수집·호출을 끊는 것은 장애를 놓칠 수 있어 따로 정한다
- **확정일**: 11/12 (사용자 결정)

<a id="d-43"></a>

### D-43 정지·해지 고객의 수집·호출

- **결정**
  - **확정(사용자 결정, Q-DM-20 닫힘).**
  - `ACTIVE`가 아닌 고객의 수집·호출.
  - **정지(`SUSPENDED`) = 끄기:** 고객 AWS의 알람·연결 스택은 그대로 둔다.
  - 이벤트는 받고 인시던트도 기록하지만 **아무에게도 호출하지 않는다**(고객 담당자·MSP 직원 모두).
  - 대신 MSP 채널에 업무 시간 요약("정지 고객 알람 N건")과 콘솔 표시.
  - `ACTIVE`로 돌리면 다음 이벤트부터 평소대로 호출하고, 정지 중 생긴 인시던트를 뒤늦게 호출하지는 않는다.
  - **해지(`TERMINATED`) = 삭제(오프보딩):** 상태를 바꾸는 순간
  - ① 호출 즉시 중단
  - ② 계정마다 `OFFBOARD_ACCOUNT` 명령으로 `ManagedBy=AlarmOps` 알람만 삭제(AlarmWriter 없으면 `CAPABILITY_DISABLED` → 수동 항목)
  - ③ 고객에게 연결 스택 삭제 요청(체크리스트)
  - ④ CloudAccount 비활성·중앙 버스 허용 목록에서 제거
  - ⑤ DB 기록은 보관 기간 뒤 삭제(기간은 Q-DM-21).
  - 해지는 되돌리지 않는다(다시 쓰려면 새로 연결).
  - **해지 뒤에도 이벤트가 오면** 인시던트·호출 없이 "정리 필요"로 MSP에 업무 시간 알림(전화 아님).
  - 새벽 전화는 계약 중인(`ACTIVE`) 고객의 장애에만 쓴다
- **이유**
  - 정지는 대개 잠깐이라 되돌릴 수 있어야 하고, 콘솔 임계값이 알람 태그(`AlarmOps:Console:*`)에 있어 알람을 지우면 설정이 사라진다.
  - 계약 밖 고객의 장애로 사람을 깨우지 않는다.
  - 정리는 급하지 않으므로 전화 대신 업무 시간 알림.
  - 정리 누락은 남은 이벤트로 드러난다
- **확정일**: 11/13 (사용자 결정)

### D-45 해지 고객 데이터 보관

- **결정**
  - **확정(사용자 결정, 11/13, Q-DM-21 닫힘).**

  - **① 오프보딩 완료 즉시 삭제:** CloudAccount 연결 정보(역할 ARN, ExternalId), 웹훅 토큰, Resource·ManagedAlarm 목록.

  - 30일 동안 ADMIN이 그 고객의 인시던트 이력을 CSV로 내보내 고객에게 돌려줄 수 있다.
  - **③ 5년 보관:** 식별할 수 없게 만든 SLA 기록만(인시던트 번호, 발생·수신·해결 시각, 심각도, 호출 성공 여부).

  - 계약서·ISMS-P 기준이 다르면 그쪽이 우선이며 기간은 설정으로 바꿀 수 있게 만든다
- **이유**
  - 개인정보와 고객 기밀은 반환 기간만 두고 지워 유출 위험을 줄인다.
  - 분쟁에 필요한 것은 사람이 아니라 시각과 결과라 가명 요약만 상사채권 시효(5년)만큼 둔다.
  - 접속기록 기준(최소 1년)에 여유를 둔다

<a id="d-35"></a>

### D-35 연락처 전체 값 열람(Reveal)

- **결정**
  - **연락처 전체 값 열람(Reveal).**
  - 사람 목록·패널은 전화번호·이메일을 가린 값으로 보여 준다.
  - ① **기본:** 전체 값은 **그 고객의 Responder만** 연다(MSP 직원은 직접 또는 템플릿 경유 Responder여야 하고, ADMIN 역할만으로는 안 됨).
  - ② **비상 예외:** 그 고객의 Responder가 아닌 **MSP ADMIN**은 **사유를 직접 입력해야만** 열 수 있다(사유 없으면 `EMERGENCY_REASON_REQUIRED`, 고르는 목록이 아니라 글로 적는다).
  - ADMIN이 아닌 직원은 예외가 없다(403 `NOT_A_RESPONDER`).
  - ③ **모든 열람(일반·비상)은 기록된다**: 누가 · 누구의 연락처 · 어느 고객 · 사유 · 언제(`ContactRevealLog`, 값 자체는 기록하지 않음).
  - 기록에 실패하면 값을 주지 않는다.
  - ④ **비상 열람은 검토 대상이다**: 검토 목록(Settings › Audit log의 `Emergency reveals`)에 모이고, 그 고객의 주 Responder에게 알림이 간다.
  - 그 사람이 범위 밖이면 다른 조회와 같이 404.
  - 포털 사용자는 자기 고객 사람의 값만 본다.
- **이유**
  - 고객 개인 연락처는 호출에 필요한 사람만 본다.
  - 30+ 고객에서 전 직원이 전 고객 연락처를 보는 것을 막음.
  - 다만 Responder가 없거나 닿지 않는 장애 때 연락할 길은 남겨야 하므로 ADMIN 비상 열람을 두고, 사유와 사후 검토로 남용을 막는다.
  - security 검토 대상
- **확정일**: 11/10 (사용자 승인), 비상 예외 추가 11/10 (사용자 결정)

<a id="d-36"></a>

### D-36 포털에서 직원은 MSP on-call

- **결정**
  - **확정(사용자 승인).**
  - 포털(고객) 사용자에게 MSP 직원은 이름 대신 **`MSP on-call`**로 보인다.
  - 포털 응답에는 내부 식별자(`contactId`, 사용자 ID, 로테이션 ID·이름, `pagingConfigId`, 업체 메시지 ID, 업체 오류 문구, 채널 ID)가 없다.

### D-55 로그인 허용 도메인·예외 주소

- **결정**
  - **확정(사용자 결정, 11/18).**
  - 콘솔 로그인(Google SSO)은 **허용 도메인**의 Google 계정만 받는다. 처음 값은 `mz.co.kr`, `megazone.com`.
  - 허용 도메인은 코드에 박지 않고 설정으로 둔다. 사용자가 원할 때 재배포 없이(또는 설정 변경만으로) 추가·삭제할 수 있어야 한다.
  - 도메인과 별개로 **예외 주소 목록**을 둔다. 개발용 특이 케이스로 개발자 개인 Gmail 주소 하나를 허용한다. 주소 값은 저장소에 적지 않고 설정에만 둔다.
  - 위 울타리는 **MSP 직원**에게 적용한다. **고객사 사람(포털)** 은 울타리와 상관없이 아래 둘 중 하나로 들어온다.
    - 사람 단위(기본): ADMIN이 그 사람의 이메일을 포털 사용자로 등록한다.
    - 고객 도메인 단위(요청이 있을 때만): ADMIN이 고객사에 로그인 도메인을 등록하면 그 도메인 사람은 그 고객의 읽기 전용 포털 사용자가 된다. 무료 메일 도메인(gmail.com 등)은 등록할 수 없다.
  - 직원 울타리와 고객 도메인이 겹치면 직원 규칙이 이긴다.
  - 허용 도메인·예외 주소는 로그인 자격일 뿐이다. 역할과 볼 수 있는 고객은 DB의 사용자 행이 정한다(사전 등록된 사용자만 들어온다).
- **이유**
  - 회사 계정만 받되, 도메인이 늘 때 코드를 고치지 않게 한다.
  - 개발자 개인 계정으로 시험할 길이 필요하다
- **확정일**: 11/18 (사용자 결정, hkjs96/alarmops#64)
