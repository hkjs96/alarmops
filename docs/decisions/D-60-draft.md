# D-60 (초안) 개발 프로세스: 독립 검증 중심의 단계별 진행

> **상태: 초안.** 사용자가 확정하면 `DECISIONS.md`로 옮기고 CLAUDE.md에는 요약 한 줄과 링크만 둔다. 근거는 `docs/research/agent-harness-2026-11.md`.

## 원칙
1. **만든 에이전트는 자기 결과를 검수하지 않는다.** 에이전트는 자기가 만든 것을 믿는 경향이 있고, 자기 테스트에 같은 가정을 담는다(근거 1).
2. **검수자는 산출물만 받는다.** 만든 쪽의 설명·추론·대화는 넘기지 않는다. 계획, diff, CI 결과, 실행 중인 앱만 준다(근거 1, 6).
3. **증거는 기계가 만든 것만 인정한다.** CI 로그, 테스트 결과 파일, 스크린샷이다. 에이전트의 "통과했다"는 보고는 증거가 아니다(근거 6).
4. **가장 무게를 두는 것은 실행 결과 검증이다.** 단위 테스트 개수나 CI 통과는 안전의 증거가 아니다(근거 1, 3).
5. **꼭 지켜야 하는 규칙은 hook·CI로 강제한다.** 문서 지시만으로 두지 않는다(근거 6).

## 단계

| 단계 | 하는 쪽 | 검수 | 넘어가는 조건 |
|---|---|---|---|
| 1. 계획 | 허브(또는 planner) | plan-reviewer(새 맥락): 명세·D-xx와 맞는지, 빠진 경우(권한·격리·실패·되돌리기)가 있는지 | **수용 기준이 검사 가능한 문장으로** 적혀 있고 [차단] 0 |
| 2. 테스트 | test-writer: 수용 기준에서 직접 만든다. 기능 코드는 건드리지 않는다 | test-reviewer: 동어반복(구현 출력을 기대값으로 씀)·과도한 mock·중복이 없는지, 기준마다 테스트가 있는지 | [차단] 0. 테스트 커밋을 따로 둔다 |
| 3. 개발 | 담당 에이전트(backend·console·infra) | CI: 기능 커밋이 2단계 테스트 파일을 바꾸지 않았는지 기계로 검사 | 테스트·타입 검사 통과 |
| 4. 코드 검수 | — | code-reviewer(diff만 받음) + security(권한·IAM·비밀·격리·워크플로 변경일 때) | [차단] 0 |
| 5. 기능 검증 | — | **verifier**: 구현을 모르는 상태로 수용 기준과 실행 중인 앱·API만 받아 직접 확인한다. 화면이면 `/persona-check`. 증거 파일을 남긴다 | 수용 기준 전부 PASS |
| 6. PR 종합 | — | pr-auditor: 수용 기준 ↔ 테스트 ↔ CI 결과 ↔ 검증 증거가 하나씩 이어지는지 대조. 이어지지 않는 기준이 있으면 [차단] | → 사용자 병합 승인 |
| 7. 배포 후 | 자동(D-59) | 스모크 검사. 실패하면 자동으로 되돌린다(실고객 연결 전 구현) | — |

## 규칙
- **왕복 제한:** 같은 단계에서 검수가 2번 반려되면 멈추고 사용자에게 보고한다. 반복 실패는 "완료" 선언으로 기우는 원인이 된다(근거 1).
- **테스트가 틀린 경우:** 3단계에서 테스트 자체가 틀렸다고 판단되면 2단계로 되돌린다. 테스트 수정은 test-reviewer가 다시 검수한다.
- **PR 크기별 축소**
  - 문서·설정만 바꾸는 PR: 4·6단계만
  - 작은 버그 수정: 1(간단히)·3·4·5·6단계
  - 권한·IAM·DB·워크플로·새 기능: 전부
- **동시 실행:** 코드 작성 에이전트는 최대 2개(기존 규칙). 검수 에이전트는 읽기 전용이라 이 제한에서 뺀다.
- **산출물 위치:** PR 댓글에 단계별로 남긴다. 증거 파일은 CI 산출물(artifact)로 둔다.

## 측정 (PoC 동안 PR마다)
- 단계별로 검수가 잡은 결함 수
- 병합 후 새어 나간 결함 수(배포 후 발견)
- PR당 걸린 시간, 토큰과 비용

4주 뒤 이 숫자를 보고 단계를 줄이거나 바꾼다. 체감은 믿지 않는다(근거 5).

## 미정 (사용자 결정 필요)
1. **5단계에 다른 회사 모델을 섞을지**
   - 같은 모델은 같은 맹점을 가진다(근거 1).
   - 섞으려면 외부 API 키와 비용이 필요하다.
   - 추천: 지금은 Claude만 쓰고, 측정 결과 5단계가 놓치는 결함이 많으면 다시 검토한다.
2. **mutation testing**
   - 에이전트 테스트 품질 개선 효과의 근거가 약하다(근거 2).
   - 추천: 지금은 도입하지 않는다.
3. **에이전트 정의 추가:** plan-reviewer, test-writer, test-reviewer, code-reviewer, verifier, pr-auditor
   - 추천: verifier와 pr-auditor를 먼저 만들고, 나머지는 측정 결과를 보고 추가한다.
4. **핵심 가드 hook을 managed settings로 옮길지**
   - 지금은 에이전트가 프로젝트 설정을 고칠 수 있다(근거 6).
   - 회사 PC 관리자 권한이 필요할 수 있다.
