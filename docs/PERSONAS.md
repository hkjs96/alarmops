# 검증 페르소나

alert-hub의 `docs/personas.md`(하은·준호·소연)를 출발점으로 하고, aws-alert-manager 쪽 사용자인 '알람 운영자'를 추가했다.
아래 P1~P3 시나리오의 §번호와 화면 이름은 alert-hub 기준이다. 새 콘솔 화면 명세(`docs/ui/`)가 확정되면 시나리오를 새 화면에 맞게 고친다.
새 콘솔은 영어이므로 시나리오의 화면 문구도 영어로 판단한다.

## P1. 온콜 엔지니어 — 하은 (내부 MSP, 인프라팀)

**상황**: 새벽 3시, Slack 핑으로 깬다. 졸리고, 화면은 하나만 볼 수 있고,
빨리 끝내고 다시 자고 싶다.
**목표**: 30초 안에 상황 파악 → 내 알람이면 Ack → 원인 확인 → 처리 후 Resolve.
**성공 기준**: 대시보드 진입부터 Ack까지 클릭 3번 이하, 헤맴 없음.

### 시나리오
1. **한눈 파악** (§6.1) — 대시보드 진입. FIRING이 몇 건인지, 그중 가장
   심각한 게 뭔지, 누가 담당인지 스크롤 없이 보이는가. FIRING 행이 시각적으로
   구분되는가.
2. **핑 → Ack** (§6.2, 2c) — FIRING 알람 상세 진입 → 무엇이 왜 터졌는지
   (메트릭·임계치·사유) 읽힘 → Acknowledge 클릭 → 상태가 바뀌고 버튼 상태도
   따라 바뀌는가. 타임라인에 기록이 남는가.
3. **내 것만 보기** (§6.1 담당 패널) — 담당 인원 패널에서 자기 이름 클릭 →
   자기가 1순위인 알람만 남는가. 해제도 직관적인가.
4. **에스컬레이션 이해** (P3) — ESCALATED 이벤트가 있는 알람에서, 왜 다음
   순위에게 넘어갔는지(몇 분 미ack) 타임라인만 읽고 이해되는가.
5. **처리 종료** — Resolve 클릭 → RESOLVED로 종료, 대시보드 수치에 반영.

## P2. 등록 관리자 — 준호 (MSP 운영 리드)

**상황**: 새 고객사 계약. 조직 트리, 담당자, 알람 순서를 세팅해야 한다.
**목표**: 신규 고객사 온보딩(고객사→프로젝트→서비스→AWS 계정→담당 2명+순서)을
왕복 없이 완료.
**성공 기준**: 온보딩 전체 5분 이내, "이건 어디서 하지?" 하는 순간이 없어야 함.

### 시나리오
1. **온보딩 풀 코스** (§6.3) — 조직 · 담당자 관리에서 고객사 신규 등록 →
   프로젝트 → 서비스 → AWS 계정(12자리) 매핑까지. 각 단계에서 다음 단계
   입구가 보이는가.
2. **담당 등록 + 순서** (§6.3/6.4) — 새 서비스에 인원 2명 배정(한 명은
   기존 인원, 한 명은 '+ 새 인원 등록' 인라인으로 신규) → 알람 처리 순서
   화면에서 순번 확인·↑↓ 교체. 등록 화면과 순서 화면의 역할 구분이 이해되는가.
3. **미매핑 복구** (§6.1) — 미매핑 계정 알람이 있는 상태에서 대시보드 배너 →
   미매핑만 보기 → ⚠ 매핑 필요 → 서비스 선택 → 매핑 후 담당이 잡히는지 확인.
4. **상속 확인** (§4) — 서비스에 직접 담당이 없을 때, 알람 처리 순서 화면이
   상위(프로젝트/고객사)에서 상속되는 순서를 보여주고, 수정하러 갈 곳을
   알려주는가.

## P3. 고객사 담당자 — 소연 (테넌트 외부, 읽기 중심)

**상황**: 고객사 소속. 우리 회사 시스템의 알람 상황만 궁금하다. 다른
고객사의 존재를 알아서도, 보여서도 안 된다.
**목표**: 우리 회사 알람만 필터해서 보고, 담당이 누군지 확인.
**성공 기준**: 자기 테넌트로 시야를 좁히는 데 성공하고, **그 시야 안에서
다른 테넌트의 데이터(인원·조직·알람)가 보이지 않아야 함**.

### 시나리오
1. **우리 것만** (§6.1) — 고객사 필터로 자기 회사 선택 → 알람 목록·담당
   패널·스탯이 자기 회사 것으로 좁혀지는가.
2. **담당 확인** (§6.2) — 알람 상세에서 지금 누가 몇 순위로 대응하는지,
   통지가 실제로 나갔는지(통지 이력) 읽히는가.
3. **테넌트 격리 — 부정 경로** (§5 데이터 격리) — 화면을 돌아다니며 다른
   고객사의 이름·인원·알람이 노출되는 지점을 적극적으로 찾는다. 담당자
   드롭다운, 로스터, 대시보드 기본 뷰(필터 없음) 포함. ※ 현재 버전은 로그인이
   없으므로 "필터를 걸었을 때의 시야"와 "드롭다운 후보 격리"를 검증하고,
   인증 없는 전체 노출은 알려진 한계로 기록만 한다.

## P4. 알람 운영자 — 민재 (MSP 클라우드 운영 엔지니어)

**상황**: 신규 고객사 AWS 계정을 연결했고, 태그 붙은 리소스마다 알람이 제대로 생겼는지 확인하고 시끄러운 알람을 다듬어야 한다. AWS 콘솔과 CloudWatch에 익숙하다.
**목표**: 커버리지 빈틈을 찾고, 임계치를 조정하고, 억제된 알림의 이유를 이해한다.
**성공 기준**: 빈틈 찾기 30초 이내, 임계치 변경 시 값의 출처(리소스 태그/콘솔/고객 기본값/기본값)와 영향 범위를 변경 전에 알 수 있어야 함.

### 시나리오
1. **연결 확인** — 고객 연결 스택 배포 후, 역할(Reader·EventForwarder·AlarmWriter)별 연결 상태와 첫 수신 시각이 보이는가.
2. **커버리지 빈틈** — 고객사 × 리소스 유형에서 알람이 없는 리소스를 찾아 알람을 만든다.
3. **임계치 조정** — 한 리소스의 임계치와 M/N을 바꾼다. 리소스 태그로 정해진 값은 편집이 막히고 이유가 보이는가. 바꾸기 전에 영향 범위를 미리 보는가.
4. **억제 이유** — 억제된 알림 하나를 골라 왜 억제됐는지(flapping, 중복, 점검 창) 화면만으로 이해되는가.
5. **밖에서 바뀐 값** — 알람이 콘솔 밖에서 바뀐 경우 표시와 변경 주체가 보이고, 복원/수용을 고를 수 있는가.

## 운영 규칙

- 기능 커밋 전: 그 기능이 건드린 페르소나의 관련 시나리오만 실행 (풀 패스 아님).
- 페이즈 종료·릴리스 전: 3 페르소나 풀 패스.
- 보고서는 P0/P1/P2 + 화면 캡처 경로 + 시나리오 번호로. "느낌"은 등급 없이
  메모로만.
- 시나리오가 스펙과 충돌하면 이 문서가 아니라 스펙(v0.3)이 이긴다 — 대신
  충돌을 이 문서에 기록한다.
