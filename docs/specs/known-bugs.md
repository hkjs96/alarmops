## 1. 수집·중복제거

**1-1. dedup이 아무 오류 없이 동작하지 않음**
- 증상: 같은 알람이 억제되지 않고 매번 나감. 오류 로그는 없음
- 원인: 수집기 역할에 `dynamodb:Query` 권한이 없었음. 조회 실패를 "알린 적 없음"으로 처리해서 아무것도 실패하지 않은 것처럼 보였음
- 커밋: ed4e005 (AAM)
- 테스트: 상태 조회가 실패하면 결과를 별도 지표로 남기는지 확인. 권한을 빼고 통합 테스트를 돌렸을 때 경보가 나야 함
- 새 구조: 저장소가 Postgres/Prisma 한 경로라 IAM Query 권한 문제는 없음(D-09). 다만 "조회 실패를 기본값으로 삼키지 않기" 원칙은 그대로 적용

**1-2. dedup이 억제 20건 뒤에 풀림 (B1)**
- 증상: 1시간에 15번 토글하는 알람이 4시간 주기가 아니라 약 10번 토글마다 다시 나감
- 원인: 마지막으로 알린 시각을 append-only 이력에서 `Limit=20`으로 스캔해 되살렸음
- 커밋: 20ebad9 (AAM), review-2026-09-07 B1 → 설계 정정 D9(상태와 이력 분리)
- 테스트: 지문 하나에 억제 이벤트 100건을 넣은 뒤 다음 발화가 여전히 억제되는지 확인
- 새 구조: 지문별 상태 행을 Postgres에 따로 두면 됨. 지문 규칙은 아직 미정(1주차)

**1-3. 미관리 알람이 한 파티션으로 몰림 (B2)**
- 증상: 고객 자체 알람이 계정 하나 안에서 전부 같은 키(`acct##metric`)를 가져 서로 dedup됨
- 원인: `identify_alarm` 실패 시 `resource_id=""`가 되고, 이 값이 `series_id`에 그대로 들어감
- 커밋: 20ebad9 (AAM)
- 테스트: 메타데이터가 없는 알람 두 개(이름이 다름)가 서로 다른 지문을 받는지 확인
- 새 구조: 소스별 지문 규칙에 "식별 실패 시 알람 ARN/이름으로 대체"를 넣어야 함

**1-4. raw 페이로드가 8,000자에서 잘려 JSON이 깨짐 (Q3)**
- 증상: 저장된 원본을 다시 파싱하지 못함
- 원인: 문자열을 길이만 보고 잘랐음
- 커밋: 20ebad9 (AAM)
- 테스트: 1MB에 가까운 페이로드를 저장한 뒤 읽었을 때 JSON으로 파싱되거나, `truncated` 표시가 붙어 있는지 확인
- 새 구조: 해당. 본문 상한은 1-6과 맞춤

**1-5. 드문드문 오는 업데이트가 저장된 필드를 null로 지움**
- 증상: CloudWatch OK 재전송(Trigger 없음) 뒤 metric·namespace·threshold·region이 사라짐
- 원인: 업데이트할 때 없는 필드를 null로 덮어썼음
- 커밋: fd67c37 (AH)
- 테스트: 발화 → Trigger 없는 OK 순서로 넣은 뒤 metric·threshold가 남아 있는지 확인. 심각도는 새 값이 있을 때만 바뀌어야 함
- 새 구조: 해당

**1-6. 같은 새 지문으로 동시에 생성하면 500 / FIRING 전이가 두 번 일어남**
- 증상: 동시 수신 시 500, count가 두 번 오르고 알림도 두 번 나감
- 원인: 유니크 충돌(P2002)을 처리하지 않았고, 상태 전이를 읽고-쓰기로 판단했음
- 커밋: fd67c37 (AH)
- 테스트: 같은 페이로드를 병렬로 20번 보냈을 때 행 1개, 알림 1회인지 확인
- 새 구조: 해당. 상태 가드를 건 `updateMany`, 또는 `INSERT … ON CONFLICT` 사용. SQS 중복 배달(D-09)에도 같은 테스트

**1-7. SNS 웹훅 SSRF / 토큰 / 본문 크기**
- 증상: 위조한 SubscriptionConfirmation으로 서버가 임의의 URL을 GET함. 헤더를 못 붙이는 SNS는 토큰 인증을 할 수 없었음
- 원인: SubscribeURL 호스트를 검증하지 않았고, 토큰 비교가 상수 시간이 아니었으며, 본문 크기 제한이 없었음
- 커밋: 02d191a (AH)
- 테스트: `https://sns.<region>.amazonaws.com`이 아닌 SubscribeURL은 거절, `?token=`도 허용, 1MB를 넘는 본문은 413
- 새 구조: 수집이 AWS(SNS/EventBridge → SQS)로 가면 공개 웹훅은 Prometheus/Grafana 수신용으로만 남음(D-06, D-09). 그 수신 엔드포인트에는 그대로 적용

**1-8. 계정→고객사 캐시가 컨테이너가 살아 있는 동안 고정됨 (Q2)**
- 증상: 계정 매핑을 바꿔도 이전 고객사로 라우팅됨
- 원인: 모듈 전역 캐시에 TTL이 없었음
- 커밋: 20ebad9 (AAM)
- 테스트: 매핑을 바꾼 뒤 TTL 안에 새 매핑이 반영되는지 확인(시계를 주입해서)
- 새 구조: 해당

**1-9. 시간 창 분석 스크립트가 14일을 넘는 창을 조용히 줄임 (B3)**
- 증상: Phase 0 분석 결과가 실제로는 14일치만 들어 있음
- 원인: CloudWatch 알람 이력 보존 기간 제한을 알리지 않았음
- 커밋: 20ebad9 (AAM)
- 테스트: 보존 기간보다 긴 창을 요청하면 경고하거나 실패하는지 확인
- 새 구조: 일회성 스크립트라 해당 없음

## 2. 억제·그룹핑

**2-1. 이벤트 단위 타이머가 폭풍 때 실행 수를 폭발시킴 (S2)**

- 커밋: 20ebad9 (AAM), 설계 D10(그룹 단위 타이머)

- 새 구조: 해당

**2-3. 플래핑 알람이 발화마다 대기 행을 쌓음**

## 3. 인시던트

**3-1. 죽은 실행의 그룹이 끝내 발송되지 않음 (H1)**
- 증상: Lambda 타임아웃 뒤 sweep으로 정리된 그룹이 알림 없이 끝남
- 원인: sweep이 finalize만 하고 라우터(Deliver)를 부르지 않았음. Deliver 재시도도 스로틀에 약했음(M2)
- 커밋: 27f20dd (AAM)
- 테스트: 처리 도중 프로세스를 죽인 뒤 다음 틱에서 그 그룹이 발송되는지 확인
- 새 구조: 해당. 틱 처리는 "미발송 그룹 재선택"이 기본 경로가 되어야 함. SQS DLQ 알림(D-10)

**3-2. 인시던트 갱신이 서로 덮어씀 (H2)**
- 증상: 라우터·ack·재알림이 동시에 쓰면 어느 한쪽의 변경이 사라짐
- 원인: 읽고-통째로-쓰기 방식이었고, 포인터 생성에도 경합이 있었음
- 커밋: 277af15 (AAM)
- 테스트: ack와 새 알림 편입을 동시에 실행했을 때 두 변경이 모두 남는지 확인(버전 컬럼 낙관적 잠금 또는 행 잠금)
- 새 구조: 해당. Postgres 트랜잭션과 `version` 컬럼

**3-3. 인시던트 축과 그룹 축이 다름 (M3)**
- 증상: 매핑되지 않은 계정이 전부 `inc##SEV-x` 인시던트 하나로 뭉침
- 원인: 인시던트 키와 그룹 키를 따로 계산했음
- 커밋: 277af15 (AAM)
- 테스트: 매핑되지 않은 계정 두 곳의 알람이 서로 다른 인시던트가 되는지 확인
- 새 구조: 해당. 인시던트 키는 그룹 키에서 파생

**3-4. 삭제된 알람의 인시던트가 영원히 열려 있고 옛 인시던트로 병합됨 (M1 포함)**
- 증상: ALARM 상태에서 삭제된 알람이 OK를 보내지 않아 인시던트가 열린 채로 남았고, 2주 동안 같은 SEV-3가 전부 그 인시던트로 쌓였음
- 원인: 해소가 OK 이벤트에만 의존했고, 자가 회복 경로가 없었으며, 병합 창에 기간 제한이 없었음
- 커밋: e04d4f6, 27f20dd (AAM)
- 테스트: 열린 인시던트의 구성 알람을 삭제하면 유예(15분) 뒤 닫히는지 확인. 오래된 인시던트에는 새 알림이 병합되지 않는지 확인
- 새 구조: 해당. 1분 틱에 "열린 인시던트 구성원 실상태 확인"을 넣음

## 4. 알람 엔진·동기화 (D-05: 재설계 없이 이식하므로 전부 회귀 테스트로 가져감)
