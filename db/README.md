# db

Prisma schema for AlarmOps (implements `docs/DATA-MODEL.md`). Postgres standard features only (D-09). Schema changes only via `prisma migrate` (D-10); never `prisma db push`.

- `prisma/schema.prisma` — the model. Constraints Prisma cannot express (partial unique indexes, CHECKs, `NULLS NOT DISTINCT`, PG15+) are appended by hand at the end of `prisma/migrations/0001_init/migration.sql`.
- `npm test -w @alarmops/db` — `prisma validate` + checks that the migrations match the schema: `0001_init` plus the generated statements of every later migration (`0002_rls`, `0003_customer_status`, …), folded statement by statement offline (`scripts/check.mjs`; it refuses DDL it cannot fold, such as DROP or ALTER COLUMN — extend it then). CI's `prisma migrate diff --from-migrations` against a shadow database is the authority.
- **New migrations from `0003_customer_status` on** (`0001_init` is no longer edited for schema changes): write the generated part from the difference of `npm run migrate:diff` before and after the schema change (or `prisma migrate dev` where the engine downloads).
- Regenerate the generated part after a schema change (before the first deploy only; afterwards add a new migration with `prisma migrate dev`):
  `npx prisma migrate diff --from-empty --to-schema-datamodel prisma/schema.prisma --script`.
  Where binaries.prisma.sh is blocked, `npm run migrate:diff -w @alarmops/db` produces the same DDL with the WASM schema engine (no DB, no native binary).
- `DATABASE_URL=… npm run seed -w @alarmops/db` — dev seed in plain SQL on `pg` (no Prisma Client engine needed; idempotent, fixed ids; refuses NODE_ENV=production). Users `usr_dev_admin|operator|viewer` are what the live dev sign-in uses.
- **`0001_init` is still edited in place — assumption: NO database has `0001_init` applied yet.** It was edited when `TickStatus` got `DEGRADED` (security review 3, N-36) and again when the SQL store was added (feat/sql-adapter): the columns that DATA-MODEL carried as "PROPOSED" (`Incident.nextEscalationAt`, `lastMergedAt`, `renotifyCount`, `projectId`, `serviceId`, `source`, `lastManualEscalationAt`; `AlertGroup.closedAt`; `NotificationJob.stepIndex`, `repeat`, `contactId`, `contactName`, `claimSeq`, `dueAt`, `providerMessageId`, `createdAt`, `seq`; `NotificationLog.attempt`, `warnings`, `errorCode`, `targetKind`, `contactId`, `seq`; `IncidentEvent.seq`; `Responder.order`; `slug` on Customer / Project / Service) and the tables `IdempotencyKey`, `UndoRecord`, `PagingConfigTombstone`, `TickClaim`, `ContactRevealLog` were folded into it, with the indexes of the tick queries. The infra workflow (`prisma migrate deploy` from GitHub Actions) is expected to be the FIRST to apply it. If any database already has it (a dev database someone created by hand counts), its checksum no longer matches and columns are missing: do not re-apply — write the difference as a new migration instead. This repository cannot tell whether such a database exists; whoever owns the dev database must check before the first `prisma migrate deploy`. From the first deploy on, every change is a new migration (`prisma migrate dev`).
- **RLS (D-40, `0002_rls`):** every table in the schema has ROW LEVEL SECURITY on, no policies, not FORCEd; the app connects as the owner and bypasses it. A non-owner role without BYPASSRLS reads 0 rows. Every new table needs `ENABLE ROW LEVEL SECURITY` in its migration; `npm run check:rls` (CI, after `migrate deploy`) fails otherwise, and `npm run test:db` checks anon / authenticated get permission denied / 0 rows while the owner reads. The store-sql suites (`packages/store-sql/test/db.ts`) and the live e2e (`apps/console/e2e-live/prepare.mjs`) apply every migration in name order; the owner bypasses RLS, so they work unchanged.
- Prisma is the MIGRATION tool only (D-10). The tick and the API read and write through `packages/store-sql` (explicit SQL on `pg`); they do not use Prisma Client. Ids are generated by the store (the schema's `cuid()` defaults exist only inside Prisma Client, e.g. for `seed.ts`).
- **Running the migration and the SQL store locally without a cloud account.**
  - `npm test -w @alarmops/store-sql` — applies `0001_init/migration.sql` to **PGlite** (`@electric-sql/pglite`, Postgres 18 compiled to WASM, in-process, installs from npm) and runs the store contract suites on it. Nothing to install or start.
  - `TEST_DATABASE_URL=postgres://… npm run test:sql -w @alarmops/store-sql` — the same suites plus the server-only tests against a real Postgres (CI: a `postgres:16` service; each test file creates its own schema from the migration and drops it). The script refuses to run without `TEST_DATABASE_URL`, so CI cannot fall back to PGlite unnoticed. A local server without Docker: the npm package `embedded-postgres` ships real Postgres binaries (`node_modules/@embedded-postgres/<platform>/native/bin`); it must run as a non-root user.
  - What PGlite does NOT show (and the real server run does): two transactions at the same time (it has one connection, so `FOR UPDATE SKIP LOCKED` never has anything to skip and lock waits cannot happen), `statement_timeout` / `lock_timeout` (accepted, not enforced), and a database clock that differs from the process clock (its `now()` IS the process clock). It is also Postgres 18, not 16: the SQL in `packages/store-sql` and the migration use nothing newer than 15 (`NULLS NOT DISTINCT`), and CI on `postgres:16` is what proves that.

## Before the first deploy (a person checks these — security review of feat/sql-adapter, R-4 / R-8)

None of this can be verified from the repository or by an agent; it needs the Supabase project and the dev database. Tick each one in the PR that first runs `prisma migrate deploy`.

1. **Supabase Data API is not a way into these tables.** Supabase exposes schema `public` over REST/GraphQL to the roles `anon` and `authenticated` by default, and a table without row-level security is then readable and writable with the anon key. This application never uses the Data API. Do ONE of: turn the Data API off (Project Settings → API), or remove `public` from its exposed schemas. As a second barrier the migration ends with `REVOKE ALL ON ALL TABLES / SEQUENCES / FUNCTIONS IN SCHEMA public FROM anon, authenticated` plus `ALTER DEFAULT PRIVILEGES … REVOKE`, inside `DO $$ … IF EXISTS (role) … $$` so that it does nothing on a plain Postgres. After the deploy, confirm with the anon key: `curl "$SUPABASE_URL/rest/v1/Contact?select=id" -H "apikey: $ANON_KEY"` must not return rows (404 / permission denied / Data API disabled).
   - Tested on a local Postgres 18 with the two roles created and granted the way Supabase grants them (`packages/store-sql/test/review-sql.test.ts`). **Not tested on Supabase**: whether Supabase's own default privileges (set for roles other than the one that runs the migration, e.g. `supabase_admin`) re-grant on later tables. So: every later migration that creates a table repeats the `REVOKE … FROM anon, authenticated` block for it, and step 1's project setting stays the first barrier.
   - **Row-level security is NOT enabled** by this migration (decision needed, below).
2. **Postgres ≥ 15 and `citext`.** `SELECT version();` must say 15 or newer (`NULLS NOT DISTINCT` is used in three unique indexes). `CREATE EXTENSION IF NOT EXISTS "citext"` is the first line of the migration: confirm the migration role may create it, or enable it first (Supabase: Database → Extensions; if it lives in schema `extensions`, that schema must be on the `search_path` of the migration and of the application role). Only Postgres 18.6 (local binaries) and PGlite have run the migration so far — not 15/16, not Supabase.
3. **`_prisma_migrations` is empty** (or absent) in every database the workflow will deploy to: `SELECT migration_name, checksum, finished_at FROM _prisma_migrations;`. `0001_init` was edited in place (see above). If a row exists, do not deploy: write the difference as `0002_…` instead. Paste the query result into the PR.
4. **Role-level limits** (hold whatever pooler is in between; the driver sets the same limits per transaction and per connection, this is the third layer): for the role the application connects as,
   `ALTER ROLE <app_role> SET statement_timeout = '4500ms'; ALTER ROLE <app_role> SET lock_timeout = '3s'; ALTER ROLE <app_role> SET idle_in_transaction_session_timeout = '15s';`
5. **Which role the application uses.** `packages/store-sql` needs SELECT / INSERT / UPDATE / DELETE on every table and USAGE on the sequences; it needs no DDL. Today the plan is one role for migration and application (Supabase: `postgres`, the owner of the tables). If they are split, grant the application role those privileges in the migration.

## Connecting (packages/store-sql `pgClient`)

| Where | Connection string | `pooler` option |
|---|---|---|
| direct connection, or a SESSION-mode pooler (Supabase port 5432) | as given | `'direct'` (default): limits are sent as startup parameters, single statements run as they are |
| TRANSACTION-mode pooler (Supabase / Supavisor port 6543, PgBouncer `pool_mode = transaction`) — what a serverless runtime should use | as given | `'transaction'`: no startup `options` are sent, **every single statement runs in its own short transaction** that sets `statement_timeout`, `lock_timeout`, `idle_in_transaction_session_timeout` and the isolation level with `SET LOCAL`; nothing is ever SET on a session |

- No session state is assumed anywhere: no `SET` outside a transaction, no temp tables, no `LISTEN`, no session advisory locks (the two advisory locks are `pg_advisory_xact_lock`, transaction-scoped), and **no named prepared statements** (node-postgres prepares only when a query is given a `name`; this package never gives one — keep it that way, a transaction pooler cannot route them).
- Every transaction starts with `SET TRANSACTION ISOLATION LEVEL READ COMMITTED`: the outbox claim relies on it and no longer on the server default.
- Waits are bounded: free connection / connect 3 s, statement 4.5 s (server) and 5 s (client, for a server that never answers), lock 3 s, idle-in-transaction 15 s, TCP keep-alive on.
- `TEST_PG_POOLER=transaction TEST_DATABASE_URL=… npm run test:sql -w @alarmops/store-sql` runs the whole suite in the transaction-pooler mode of the driver (against a plain server: it shows that nothing depends on session state, not that a particular pooler accepts everything). **Not verified against a real Supavisor/PgBouncer** — run this command once with the port-6543 URL of the dev project before relying on it.
- The Prisma driver (`drivers/prisma.ts`) is still unexercised.

## Decisions needed

- **RLS as a second barrier?** `ALTER TABLE … ENABLE ROW LEVEL SECURITY` on every table with no policies would shut `anon` / `authenticated` out even if a grant came back. It does not affect a role that owns the tables or has BYPASSRLS (Supabase `postgres`), and it would silently return zero rows to an application role that is neither. Options: (a) REVOKE only — what is implemented; (b) REVOKE + RLS without policies, with the application role = table owner (recommended once item 5 above is settled, as a new migration); (c) RLS with `FORCE` and policies per tenant — a different design (DATA-MODEL says authorisation is not done with RLS).
